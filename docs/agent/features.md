# Agent Features

This catalog records what each Grida Agent capability does, the outcome it
should preserve, and the limits that affect use. The current column names
legacy or native behavior where they differ. Native Desktop availability
depends on the build and selected connection. The source-built host supports
headless runs and ACP clients as described in the [client guide](./clients.md).

**Partial** identifies narrower availability or behavior. **Deferred** marks
a deliberate scope limit. **Open** marks a capability whose product behavior
still needs a decision. Linked scenarios and tests record the evidence behind
the described behavior. Release availability follows the named build and client.

Where Desktop switches to the native runtime, it archives prior chat data and
starts a fresh store. Native history features apply to chats created there.

## Supported surfaces

Desktop and headless execution are the supported agent surfaces. The desktop
client can use web-rendered UI while its agent executes through the native host.
Hosted browser assistants are unavailable under the desktop-first scope.

| Retired surface      | What it provided                                                     | Disposition                                                                                    |
| -------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Web SVG assistant    | Hosted chat and tool execution for the browser SVG editor.           | Hosted execution, chat panel and assistant controls removed. SVG editing and storage retained. |
| Web canvas assistant | Hosted chat and design-tool execution for the browser canvas editor. | Hosted execution and the Agent tab removed. Canvas editing and inspector retained.             |

The development browser bridge for Desktop pages was also removed. Open those
pages in Desktop or use the native host for [headless development](./clients.md).

## Checking coverage

Review each capability from accepted input through authority, execution,
observation, interruption, recovery, and eventual retention or deletion. Check
its interaction with concurrent work and unavailable dependencies. A missing
answer belongs in the owning contract before another feature label is added.

The [experience scenarios](../wg/ai/agent/experience.md#judge-the-experience-by-outcomes)
describe observable outcomes, including failures and interrupted work. Existing
test coverage and remaining proof live in the
[harness assessment](https://github.com/gridaco/grida/blob/main/packages/grida-ai-agent/docs/rust-core-pressure-test.md#existing-harness-assessment)
and [regression obligations](https://github.com/gridaco/grida/blob/main/packages/grida-ai-agent/docs/rust-core-pressure-test.md#regression-obligations).

## Keeping this compact and current

- Update a feature's row in the same change that introduces, changes, or retires
  its user-visible behavior. Elaborate the behavior in the linked document.
- Describe the situation and observable result in product terms. Preserve the
  reason for a surprising rule and the limits that affect use. Keep internal
  functions, storage details, and test procedures in their engineering owners.
- Update current coverage from the real entrypoint and its evidence. Mark a
  feature Available in release documentation only with a named host and release
  plus acceptance evidence. Keep target contracts separate from that claim.
- Give each user-visible capability one row. Implementation choices and internal
  components belong in the engineering documents.
- Keep FAQ answers and guides derived from this catalog and their linked
  behavior contracts. Resolve disagreements in those owners first.
- Automating or retiring a manual test changes its verification method. The
  feature's promise remains in its canonical description until the product
  behavior itself changes.
